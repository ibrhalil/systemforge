# backend/AGENTS.md

## Module

Spring Boot application — controller/service/security/config. Depends on `common` + `persistence`. Only this module produces an executable jar (`forgesys-backend.jar`). General rules from the root AGENTS.md apply.

For commands see [README](../README.md#build-komutları). Backend summary: `./mvnw -pl backend spring-boot:run` (NOT from root, always `-pl backend`), `./mvnw -pl backend test -Dtest=ClassName#method`.

## Tenant Context rules (CRITICAL)

- `TenantFilter` (`OncePerRequestFilter`): Host header -> subdomain -> `CompanyRepository.findBySubdomain` -> `schemaName` -> `TenantContext`. Only `ACTIVE` Companies are resolved (`PROVISIONING`/`SUSPENDED`/`TERMINATED` are not).
- `shouldNotFilter()` exempts only `/api/v1/auth/company/**` (tenant creation — no tenant yet), `/api/v1/platform/**` (platform API is tenant-agnostic — K-50) and `/actuator/**`. Login (`/api/v1/auth/login`), `/me` and `/auth/platform-switch` ARE tenant-specific and go through normal subdomain resolution.
- **Do NOT validate tenant in the controller** — the filter is the single responsibility owner.
- When tenant context is null the resolver returns `"public"` -> public-schema data (Company) is reachable.
- Services that programmatically switch the tenant MUST use `tenant/TenantContextExecutor` — it owns BOTH sanctioned windows: `inTenantContext(schemaName, action)` (set-and-restore — restores the caller's context, clears when there was none) and `withoutTenantContext(action)` (public-schema window: runs the action with NO tenant context, restores afterward). Hand-rolling the `setCurrentTenant`/`clear` pair is forbidden ([RISK-10]: a missing restore leaks the tenant across pooled threads). Current users: `ModuleActivationService`, `TenantSampleDataService`, `TokenPurgeJob`, `PlatformCompanyService` + `PlatformSwitchService` (both `withoutTenantContext` for `public`-schema access), plus `TenantProvisioningService.createAdminUser` (plain set + `clear()` in `finally`).
- The `X-Tenant-ID` header fallback is active **only in the `dev` profile**. Fully disabled in prod.
- `TenantContext` is NOT propagated automatically across `@Async` threads — a `TaskDecorator` is required ([RISK-10](../docs/DECISIONS.md#risk-10)). **Deferred** to after Phase 2.3 auth (no `@Async` consumer yet; `@EnableAsync` absent).

## Endpoint rules

- All endpoints live under the `/api/v1/*` prefix.
- Return a response DTO (`record`); entities MUST NOT be exposed directly. No `Map<String,Object>` returns (the last one, `AuthController.registerCompany`, already returns `CompanyRegisterResponse`; MapStruct was cancelled — manual `toResponse` convention, [K-37](../docs/DECISIONS.md#k-37)).
- **Paged lists** return the API-owned `PageResponse<T>` (`dto/PageResponse.java`): `{data: [...], meta: {page, pageSize, totalElements, totalPages, hasNext, hasPrevious}}` (`meta.page` 0-based). No raw Spring Data `Page<T>` is serialized anymore — the wire contract is ours, not the framework's. **K-37 pagination rule:** every DB-backed collection that can grow returns `PageResponse` (users/roles/groups/permissions/projects/tasks/apps/app-records/audit-logs/login-history). Documented `List<T>` exceptions: app properties/views (design-bounded nested resources) and the session lists (Redis read model — DB paging is meaningless there).
- **Sorting is whitelisted.** Every paged list endpoint runs its `Pageable` through `web/SortGuard.require(...)` against the feature's `FilterFieldSet` (registered with generated metamodel constants, e.g. `User_.EMAIL` — renames break the build). Unknown sort properties map to 400 `validation_error` via the `PropertyReferenceException` handler; nested property paths (e.g. `userAccount.enabled`) are rejected by the guard itself.
- **Search & filter engine** (`web/filter/`, K-49): `SearchRequest {page, size, sorts[], filters[], q, qFields[]}` + `FilterCriteria {field, operator, values[]}` (14 operators: EQ/NOT_EQ/IN/NOT_IN/CONTAINS/STARTS_WITH/ENDS_WITH/GT/GTE/LT/LTE/BETWEEN/IS_NULL/IS_NOT_NULL). **K-55 `GET ?sq=` (split wire):** every GET list endpoint ALSO accepts the FILTER part of the query as one URL-safe-base64 JSON blob in the `sq` param (`web/filter/SearchQueryArgumentResolver` → `SearchQuery` wrapper) — `{v, q, qFields, filters}` only; **paging and sorting always travel as ordinary flat params** (`?page=&size=&sort=field,dir`), resolved by Spring's `Pageable` + the endpoint's single `SortGuard.require` for both paths. Precedence: `sq` present → its `q`/`filters` win over the flat `q` and scoped filter params. Malformed/oversized (cap `forgesys.web.search-query.max-length`, default 4096) → 400 `validation_error` (`SearchQueryDecodingException`). Unknown JSON fields tolerated (lenient decode — the blob's `v:1` marker and legacy all-in-one blobs' page/size/sorts are ignored). POST body sorts use `{field, direction}` — the FE `SortState.direction` rename keeps the shapes identical. OUT of `sq`: custom-app records (JSONB engine, different contract) and platform service-accounts (no q/filters registrations; an sq carrying q/filters → 400). Fields register per kind: DIRECT (root attribute), JOINED (to-one LEFT-join leaf — e.g. a user's `firstName` via the profile), SUBQUERY (correlated scalar — counts over plural associations, name resolution through plain FK columns), MEMBERSHIP (collection contains: IN/NOT_IN/IS_NULL=is-empty/IS_NOT_NULL → correlated EXISTS; **inverse form** when the join table is owned by the other side). Wire names stay FLAT (nested `a.b` paths remain structurally unreachable — SortGuard rejects them); resolution data lives in compile-time registrations only. The field's `FilterFieldType` (STRING/UUID/BOOLEAN/TEMPORAL/DATE/NUMERIC/INT/ENUM) decides supported operators and value parsing (parse failure → 400); membership fields are never sortable (`sortable` flag) and SortGuard lists the sortable names on rejection. Hard limits: ≤10 filters, ≤5 sorts, IN ≤100 values, size ≤100. The GET lists accept `?q=` (global OR-CONTAINS over registered searchable fields) and `?qFields=` / body `qFields[]` (smart-search targeting — narrows `q` to selected searchable fields, unknown/non-searchable → 400). EVERY list surface also carries `POST /{resource}/search`. Audit GETs (`action`/`actorId`/`userId`/`success`) are translated into engine criteria and AND-combined.
- **Projected list reads (K-49)** (`web/projection/ProjectionListQuery`): every DB-backed list runs as a Criteria DTO projection — one content query (`cb.construct`, no entity hydration) + one count query with the same predicate; sort properties resolve through the feature's `FilterFieldSet` so joined/subquery columns sort in the DB like direct ones. Flatness rule: JOINED targets to-one associations ONLY and SUBQUERY must stay scalar — collection data goes through subqueries/EXISTS (a to-many join would multiply rows and silently break paging). Per-feature executors live in `service/` (`UserDirectoryQueryExecutor`, `GroupListQueryExecutor`, `RoleListQueryExecutor`, `NoteListQueryExecutor`, `CustomAppListQueryExecutor`, `ProjectListQueryExecutor`, `TaskListQueryExecutor`, `PermissionListQueryExecutor`, `NoteCategoryListQueryExecutor`, `PlatformCompanyListQueryExecutor`); batched summary lists (group roles/members, role permissions/parents) resolve in ONE extra query per kind per page.
- **`POST /{resource}/search` on EVERY list surface (K-49):** users, roles, groups, permissions, projects, `projects/{id}/tasks`, notes, `projects/{id}/notes`, note-categories, `projects/{id}/note-categories`, apps, `projects/{id}/custom-apps`, audit-logs, login-history, request-logs and platform/companies each expose the full-body filter-engine variant under the SAME read permission as their GET list. GET lists keep their legacy scoped params (`?categoryId=`, `?pinned=`, `?projectId=`, `?success=` ...) for bookmarkable reads.
- Errors use the uniform `ApiErrorResponse` (`GlobalExceptionHandler`): every error path returns `{timestamp, status, error, code, message, path, traceId, fields[]}`. `code` is a stable `ErrorCode` (lowercased enum name, e.g. `auth_bad_credentials`) — clients branch on it; message/status may evolve. Sensitive rejected values (`password`/`token`/`secret`/`credential`) are masked to `[REDACTED]` in field errors. `BusinessException` (`AuthException`/`ResourceNotFoundException`) carries an `ErrorCode`; `TenantNotFoundException` stays a plain `RuntimeException` in `common` and is translated by the handler. `traceId` comes from MDC, populated per request by `RequestMetadataFilter` (K-19; honors `X-Request-Id` or generates a UUID); before that filter runs, `ApiErrorFactory` generates one per error. Client-error mappings (Faz D): malformed path/query params (`MethodArgumentTypeMismatchException`, `MissingServletRequestParameterException`, `jakarta.validation.ConstraintViolationException`) → 400 `validation_error`; concurrent uniqueness races (`DataIntegrityViolationException`) → 400 with the precise `*_TAKEN` code (constraint-name substring map: `users_email`→`user_email_taken` etc.) or `business_error` fallback — never 500.
- Bean Validation (`@Valid` + `@NotBlank`/`@Pattern`/`@Email`).

> `PermissionController` is full CRUD. The built-in catalog is still seed-driven (`PermissionCatalog` + `RbacSeeder`), but admins can also create runtime permissions — the name MUST match `^[a-z][a-z0-9]*:[a-z][a-z0-9-]*:[a-z]+$` (`{module}:{resource}:{action}`). Deletion is blocked while a permission is still assigned to any role (`permission_in_use`, 409) — unassign from roles first. The `effective-permissions` endpoints resolve the full chain (direct + active-group roles + transitive parent inheritance) into sorted permission-name strings, backing the detail-page "what can this user/group actually do" views.

> **User directory read path (K-49):** `GET /users` (+`?qFields=`) and `POST /users/search` return the flat `UserDirectoryViewResponse` (id/username/email/emailVerified/first/last/enabled/lastLoginAt/createdDate/roleCount/groupCount) via `UserDirectoryQueryExecutor` — a Criteria DTO projection over the User root (profile/account to-one LEFT joins + correlated count subqueries; the former `@Immutable @Subselect` `UserDirectoryView` entity was REMOVED). Registrable columns: direct attrs, joined profile/account fields, `roleCount`/`groupCount` subquery scalars (filter+sort), and `roleIds`/`groupIds` membership filters. Soft-delete semantics ride the joined entities' soft-delete filter; counts exclude soft-deleted roles/groups. The DETAIL endpoints (`GET /{id}`, effective-permissions) still resolve the full `UserResponse` with role/group sets via the entity path. List rows are counts; modals that need the current assignments fetch the detail themselves.
>
> **Scoped user visibility (`iam:group-member:read`):** read endpoints accept EITHER `iam:user:read` (full tenant — existing behavior) or `iam:group-member:read` (members of the caller's own groups + self). > **All-permissions flag (`t_roles.all_permissions`, tenant `V1__baseline.sql`):** a role carrying the flag implicitly holds EVERY permission in the tenant, resolved dynamically by `CustomUserDetailsService.resolvePermissionNames` (checked after the parent-role closure, so inheritance from an all-permissions role is all-permissions too). Creating/renaming a permission calls `SessionRevocationService.revokeAllPermissionsRoleHolders` so all-permissions users pick up the new/renamed name on their next request rather than at access-token TTL.

> **Auth stack:** RS256 JWT (starter present; auto-config filter NOT enabled — custom `JwtAuthenticationFilter`, [RISK-14](../docs/DECISIONS.md#risk-14)). `JwtTokenProvider` mints tokens (sub=userId; claims: email/tenant/authorities/jti) + the platform variants (`scope=platform`, no tenant claim; impersonation: `act`/`act_email`/`imp`). The filter, in order: cookie/header decode → `scope=platform` branch (platform cookie wins when both are present; revocation via `PlatformUserRepository.findTokenInvalidBefore` — the branch MUST split BEFORE the tenant lookup, `public.t_users` does not exist; context must be tenant-less) → tenant claim == `TenantContext` ([RISK-19](../docs/DECISIONS.md#risk-19)) → `tokenInvalidBefore` check (user-scoped revoke, single-column projection; set by password change/reset, privilege-change revoke, lockout, disable/delete) → `jti` blacklist check (granular per-session revoke, `TokenBlacklistService` Redis `bl:jti:{jti}`) → `CustomUserDetails` into `SecurityContext`. Before it, `PlatformApiKeyAuthenticationFilter` (chain order in `SecurityConfig`: rate-limit → api-key → jwt) authenticates `X-API-Key` requests statelessly: header-only match (never on `/platform/auth/*`), active tenant context → 401 BEFORE any DB hit (RISK-19 symmetry), prefix lookup (`@EntityGraph` fetch) → constant-time `TokenHasher` compare → scope authorities as `scope=platform` principal; every failure is a uniform 401 `platform_api_key_invalid` + platform audit row. `CustomUserDetailsService` (login/refresh only) resolves authorities = direct roles + active group roles → permissions. RSA keys: configured PEMs in prod (fail-fast if missing, [RISK-23](../docs/DECISIONS.md#risk-23)), ephemeral in dev/test — never commit `certs/*.pem`.
>
> **Refresh tokens (K-34):** opaque, Redis SHA-256 hash-at-rest, atomic Lua rotation + reuse detection (reuse → revoke all + `tokenInvalidBefore` → `auth_refresh_token_reuse`). `POST /auth/refresh` re-resolves authorities from DB (locked/disabled re-check). Per-session logout consumes the refresh + blacklists the access `jti`. Store impls are `@Profile`-split (`Redis*` dev/prod, `InMemory*` test — Docker-free build); real Redis verified by gated `RedisRefreshTokenIT`. **Redis-outage behavior (deliberate, [RISK-36](../docs/DECISIONS.md#risk-36)):** rate-limiter + blacklist fail-open (no 500s); `rotate` degrades to a clean 401, session list/revoke to empty/false; only `issue` fails closed (`DataAccessException` → 503 `service_unavailable`).
>
> **Brute-force lockout ([RISK-22](../docs/DECISIONS.md#risk-22)):** 5 failed attempts / 15 min → 423 `auth_account_locked`; lock also stamps `tokenInvalidBefore` (outstanding access tokens die immediately) and blocks refresh. The formerly deferred tenant user email verification + password reset landed as [K-48](../docs/DECISIONS.md#k-48) (`t_auth_tokens`, tenant V4). Deferred: PermissionCacheService (low value — authorities are embedded in the JWT).

> **Two-phase signup flow (K-21) — IMPLEMENTED:** `POST /api/v1/auth/company/register` returns 202 with a `PROVISIONING` Company + issues a `TenantVerificationToken` (admin credentials pre-hashed into the token). `POST /api/v1/auth/company/verify` consumes the token, runs `CREATE SCHEMA` + programmatic Flyway + admin user, and promotes the Company to `ACTIVE`. `TenantProvisioningService` is split into `createPendingCompany` + `verifyAndProvision` (both `@Transactional`; DDL inside `verifyAndProvision` is an implicit commit, see [DEBT-10](../docs/DECISIONS.md#debt-10) partial). Details in [DECISIONS.md K-21](../docs/DECISIONS.md#k-21) + [K-32](../docs/DECISIONS.md#k-32) (email_domain dropped, 1:N org domains).

> **Audit & log (K-19 + K-27) — IMPLEMENTED:** 3-layer log. Layer 1: `@AuditLog` AOP (`AuditLogAspect`) writes `t_audit_logs` on admin writes across all services (actor from SecurityContext, IP/traceId from `RequestContext`; `captureDelta = true` persists before/after name sets at privilege-change points). `t_audit_logs` + `t_login_history` are append-only (DB `BEFORE UPDATE OR DELETE` trigger). Layer 2: `LoginHistoryService.record(...)` writes `t_login_history` for every login attempt (success + failure; `reason` = `ErrorCode.code()`). Layer 3: `RequestMetadataFilter` (`-102`) populates `RequestContext` + MDC `traceId`; `RequestLogFilter` (`-95`, INSIDE the security chain) + `RequestBodyCaptureFilter` (`-94`) write `t_request_logs` (metadata every request; masked body on high-risk mutating paths — `forgesys.audit.high-risk-paths`, `password`/`token`/`secret` → `[REDACTED]`). Read side: `GET /audit-logs` + `GET /login-history` + `GET /request-logs` (`iam:audit:read`). All writes `REQUIRES_NEW` + best-effort. Deferred K-27 parts (LOW): approval workflow (`t_pending_actions`) + anomaly detection — [DECISIONS.md K-27](../docs/DECISIONS.md#k-27).

- **[Faz 1] Privilege-change session revoke (`SessionRevocationService`):** authorities are embedded in the access token at issue time, so a role/permission/group mutation otherwise keeps affected tokens authoritative until their next issue (up to the TTL). `SessionRevocationService` closes that privilege-retention window: it bulk-stamps `tokenInvalidBefore` (kills outstanding access tokens, [RISK-21]) and drops refresh tokens (`RefreshTokenStore.revokeAllForUser`) for every affected user. Wired into: `UserService.setRoles`/`setGroups` (target user) + `changePassword`/`resetPassword`/`revokeTokens` (delegated, was the old in-place `invalidateTokens`); `RoleService.setPermissions`/`delete` (`revokeRoleHolders` — direct role + active group-role bearers, resolved BEFORE soft-delete so the soft-delete filter doesn't hide them); `GroupService.setRoles`/`delete` (`revokeGroupMembers`, before soft-delete) + `update(active=false)` (deactivation) + `setMembers` (only **removed** members lose permissions — added members gain on next login, no revoke). Name/description `update`s do NOT revoke (no permission change). Revoke is best-effort alongside the business op (same tx). **All-permissions refresh:** `revokeAllPermissionsRoleHolders` (every holder of an `all_permissions` role) is fired from `PermissionService.create`/`update`-on-rename so all-permissions users pick up a new/renamed permission on their next request. **[Faz 5a]** The service also enforces the concurrent-session cap (`enforceSessionLimit`, called from `AuthService.login` after issue): `forgesys.security.max-sessions` (`<=0` = unlimited); when a login pushes the user over the cap the oldest sessions are evicted via the existing K-28 `listSessions`/`revokeSession` primitives — login always succeeds, no store-contract change.

## Gotchas

- **`AuditorAware` reads the authenticated user's id** from SecurityContext (`MultiTenancyJpaConfig`), falling back to `"system"` when there is no authenticated principal — tenant signup, provisioning, and startup runners ([RISK-33](../docs/DECISIONS.md#risk-33), [RISK-3](../docs/DECISIONS.md#risk-3) resolved).
- **`SecurityConfig`** (Epic 2.3 — DONE): `spring-boot-starter-security` is now present. The `SecurityFilterChain` is STATELESS + CSRF-disabled, permits `/api/v1/auth/company/**` + `/api/v1/auth/login` + the platform auth endpoints (`/api/v1/platform/auth/login|refresh`, `/api/v1/auth/platform-switch`) + actuator health/info, authenticates the rest, and wires the JSON `RestAuthenticationEntryPoint`/`RestAccessDeniedHandler`. `@EnableMethodSecurity` is active ([K-26](../docs/DECISIONS.md#k-26)) so `@PreAuthorize` is enforced on `iam:*` endpoints and on the platform surface (`platform:*` authority AND `scope == 'platform'` — platform tokens on tenant endpoints and tenant tokens on platform endpoints both 403). The password encoder is a `PepperingPasswordEncoder` ([K-23](../docs/DECISIONS.md#k-23)): BCrypt strength 12 (RISK-13) keyed with a global pepper via HMAC-SHA256 pre-hash so a DB leak alone cannot brute-force hashes. The pepper is read from `forgesys.security.password-pepper` / `PASSWORD_PEPPER` env var; a blank value fails startup fast (the `test`/`dev` profiles ship a non-secret default). Legacy pepper-less BCrypt hashes (pre-K-23) still validate and are lazily rehashed to the peppered format (`{sf-peppered}` marker) on the next successful login (`AuthService.upgradeHashIfNeeded`).
- **`TenantFilter` runs before the security chain** via a `FilterRegistrationBean` at order `-101` (security is at `-100`) in `SecurityConfig`, so tenant context is resolved before the JWT auth filter executes. The registration also suppresses the bare `@Component` filter's default low-precedence auto-registration.
- **`RequestMetadataFilter`** (K-19) runs BEFORE the tenant filter at order `-102` (tenant `-101`, security `-100`) via a `FilterRegistrationBean`, capturing `X-Request-Id` (or a generated UUID), client IP (`X-Forwarded-For` first hop / `X-Real-IP` / `getRemoteAddr`) and User-Agent into `RequestContext` + MDC `traceId`. Both are cleared in `finally` (no ThreadLocal leak). All requests go through it (incl. actuator).
- **`RequestLogFilter` (`-95`) + `RequestBodyCaptureFilter` (`-94`) run INSIDE the security chain** (after the security DelegatingFilterProxy at `-100`) via `FilterRegistrationBean`s in `SecurityConfig` — the request-log write happens in the filter's `finally`, which unwinds BEFORE the security/tenant/metadata filters clear their ThreadLocals, so tenant schema, authentication and request metadata are live when the `t_request_logs` row is written. **Do NOT put these filters on bare `@Order` outside the chain** — `@Order(HIGHEST_PRECEDENCE + n)` once placed them outermost, the write landed in `public` with null user/trace, and the swallowed 42P01 left the request-logs screen empty (regression-locked by `RequestLogFilterChainTest`). The write is skipped when no tenant was resolved (actuator, tenant signup, unknown host). `RequestBodyCaptureFilter` publishes the masked body to `AuditRequestContext` BEFORE delegating (consumed by `AuditLogAspect` via peek during the request); `RequestLogFilter`'s finally is the single clear point (no ThreadLocal leak across reused threads). Requests rejected inside the security chain itself (401 before `-95`) are not logged — failed logins are covered by `t_login_history`.
- **REQUIRES_NEW audit writes + `@Transactional` tests:** `AuditService` / `LoginHistoryService` run `REQUIRES_NEW`, so during `@SpringBootTest` controller tests their writes commit outside the test's rollback and pollute the shared cached-context H2. Tests asserting on `t_audit_logs` / `t_login_history` must use membership (`hasItem`) + unique sentinels, NOT positional / count assertions (see `AuditControllerTest`).
- CORS is configured in `CorsConfig` (`CorsConfigurationSource`, `allowCredentials=true`, origins via `forgesys.security.cors.allowed-origins`, default Vite `http://localhost:5173` + `http://localhost:3000`). Required because auth is cookie-based.
- **`TenantContextExecutor` owns BOTH sanctioned tenant-context windows** (K-25/K-50): `withoutTenantContext(action)` — the ONLY sanctioned public-schema window (runs with NO tenant context, restores afterward; users: `PlatformCompanyService`, `PlatformSwitchService`) — and `inTenantContext(schemaName, action)` — the only sanctioned tenant-switch window. Do not hand-roll `setCurrentTenant`/`clear` pairs elsewhere; a missing restore leaks the tenant across pooled threads ([RISK-10](../docs/DECISIONS.md#risk-10)).
- **Spring Boot 4.1 / Spring Security 7 gotchas:** test slice annotations (`@WebMvcTest`, `@AutoConfigureMockMvc`, `@DataJpaTest`) were REMOVED from the standard autoconfigure — build MockMvc via `MockMvcBuilders.webAppContextSetup(wac).addFilters(securityFilter)` or use `@SpringBootTest` + a real port. Jackson is v3: `ObjectMapper`/databind moved to package `tools.jackson.*` (annotations stayed at `com.fasterxml.jackson.annotation`). `SecurityProperties` moved to `org.springframework.boot.security.autoconfigure` and lost `DEFAULT_FILTER_ORDER` (use literal `-100`).
- The `CompanyStatus` enum: `PROVISIONING`, `ACTIVE`, `SUSPENDED`, `TERMINATED`. K-21 activates `PROVISIONING` (phase 1 sets it; phase 2 `verifyAndProvision` promotes to `ACTIVE`). `PlatformCompanyService.updateStatus` can flip to `SUSPENDED`/`TERMINATED` manually; full lifecycle (billing-driven) arrives in Faz 6.
